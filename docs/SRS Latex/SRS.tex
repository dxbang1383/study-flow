\section*{Section 1. Overview}

\subsection*{1.1 Purpose}
The purpose of this Software Requirements Specification (SRS) document is to provide a detailed overview of the Study-Flow web application. It describes the system's functional and non-functional requirements, its architecture, and its external interfaces. This document is intended for developers, project managers, and stakeholders to understand the complete scope of the Study-Flow system.

\subsection*{1.2 Project Scope}
Study-Flow is a comprehensive study management web application designed to help students and professionals organize their tasks and track their study time efficiently. The platform features an interactive Kanban board for task management, a Pomodoro-style timer for focused study sessions, and a real-time dashboard for overviewing progress. It is built using React for the frontend and FastAPI for the backend.

\section*{Section 2: Overall Description}
\subsection*{2.1 Product Perspective}
Study-Flow is a standalone, full-stack web application. The frontend is an SPA communicating via RESTful HTTP requests to the FastAPI backend. Data persistence is handled by an SQLite database through SQLAlchemy ORM.

\subsection*{2.2 Product Function}
The main functions of the system are:

\vspace{0.3cm}
\noindent
\renewcommand{\arraystretch}{1.5}
\begin{xltabular}{\textwidth}{|l|X|}
\hline
\textbf{Function} & \textbf{Description} \\ \hline
User Authentication & The user registers, logs in securely, and updates profile information using JWT. \\ \hline
Manage Tasks & The user creates, edits, deletes, and tracks tasks across different statuses using a Kanban board. \\ \hline
View Dashboard Progress & The user views overall study statistics, completed tasks, and current streaks on a dashboard. \\ \hline
Manage Study Timer & The user starts, pauses, and completes Pomodoro timer sessions to track focused study time. \\ \hline
Persist Local State & The system stores tasks, timer progress, and user data locally and synchronizes with the backend database so that information can be restored after the application restarts. \\ \hline
\end{xltabular}
\vspace{0.3cm}

\subsection*{2.3 Users Of The System}
Study-Flow implements user accounts and secure authentication. All authenticated users can access the main functions (Task Management, Pomodoro Timer, Dashboard Progress) to organize their study workflows.

\vspace{0.3cm}
\noindent
\renewcommand{\arraystretch}{1.5}
\begin{xltabular}{\textwidth}{|l|X|}
\hline
\textbf{Attribute} & \textbf{Detail} \\ \hline
Technical level & Basic to intermediate, able to use web applications and navigate intuitive interfaces \\ \hline
Main actions & Register/login, create and manage tasks on a Kanban board, control the Pomodoro timer, and view progress on the dashboard \\ \hline
Access level & Full access to their own tasks and study data (no administrative privileges required) \\ \hline
Environment knowledge & Knows how to use a standard web browser on desktop or mobile devices \\ \hline
\end{xltabular}
\vspace{0.3cm}

\subsection*{2.4 Operating Environment}
\begin{itemize}
    \item Operating system: Windows, macOS, Linux, iOS, or Android
    \item Delivery format: web application accessible via standard browsers
    \item Network: internet connection is required for API communication
    \item User interface: responsive web user interface
    \item Input devices: keyboard, mouse, or touch screen
    \item Storage: local storage for JWT tokens and SQLite database on the server
\end{itemize}

\subsection*{2.5 Constraints}
\begin{itemize}
    \item The application must be accessible on modern web browsers.
    \item The frontend state management must be handled by Zustand.
    \item The drag-and-drop functionality must be implemented using react-dnd.
    \item The backend must process requests concurrently using FastAPI's async capabilities.
    \item User passwords must be securely hashed using bcrypt before storage.
    \item The database schema must be managed using SQLAlchemy ORM.
\end{itemize}

\subsection*{2.6 Assumptions And Dependencies}
\subsubsection*{2.6.1 Assumptions}
\begin{itemize}
    \item The end-user has a stable internet connection.
    \item The user's device clock is accurate for timer functionalities.
\end{itemize}
\subsubsection*{2.6.2 Dependencies}
\begin{itemize}
    \item The drag-and-drop UI depends on the \texttt{react-dnd} library.
    \item Frontend state management relies on \texttt{zustand}.
\end{itemize}

\subsection*{2.7 User Needs}

\vspace{0.3cm}
\noindent
\renewcommand{\arraystretch}{1.5}
\begin{xltabular}{\textwidth}{|p{4.5cm}|X|X|}
\hline
\textbf{User Need} & \textbf{Why it matters} & \textbf{How the system handles it} \\ \hline
Organize tasks visually & Users need to quickly see what tasks are pending, in progress, or completed to manage their workload effectively & The system provides an interactive Kanban board with drag-and-drop capabilities across different status columns \\ \hline
Maintain focus during study sessions & Users often struggle with distractions and need a structured way to concentrate & The system integrates a Pomodoro timer to enforce structured study and break intervals \\ \hline
Track learning progress over time & Users need motivation and insights into how much time they have spent studying & The Dashboard displays aggregate statistics, completed tasks, and study streaks \\ \hline
Securely access personal data from anywhere & Users want their study data to be private, safe, and accessible across different devices & The app requires secure JWT authentication and persists all data safely to a backend database \\ \hline
Avoid losing temporary state & Users should not lose their timer progress or task updates if they accidentally refresh the page & The frontend utilizes Zustand and local storage to sync and persist application state \\ \hline

\section*{3. Specific Functional Requirements}

\subsection*{3.1 User Authentication}

\renewcommand{\arraystretch}{1.5}
\begin{xltabular}{\textwidth}{|p{4cm}|X|}
\hline
\textbf{Use Case Name} & \textbf{User Authentication} \\ \hline
\textbf{XRef} & Section 2.2 — Product Functions; Section 2.5 — Constraints \\ \hline
\textbf{Actor} & User \\ \hline
\textbf{Trigger} & The user opens the login/register page to access the system. \\ \hline
\textbf{Precondition} & None (for register); User account exists (for login). \\ \hline
\textbf{Basic Path} & 1. The user navigates to the login/register page. \newline 2. The user enters their username and password. \newline 3. The user clicks submit. \newline 4. The system validates the input. \newline 5. The system creates the account or verifies credentials. \newline 6. The system generates a JWT token and stores it locally. \newline 7. The system redirects the user to the Dashboard. \\ \hline
\textbf{Alternative Paths} & If the username already exists during registration, the system shows an error message. If the password is incorrect during login, the system shows an "Invalid credentials" error. \\ \hline
\textbf{Postcondition} & The user is authenticated and redirected to the main application. \\ \hline
\textbf{Exception Paths} & The backend server is unreachable; the system displays a network error. \\ \hline
\textbf{Other} & Passwords must be hashed using bcrypt before being stored. \\ \hline
\end{xltabular}

\subsection*{3.2 Manage Tasks}

\renewcommand{\arraystretch}{1.5}
\begin{xltabular}{\textwidth}{|p{4cm}|X|}
\hline
\textbf{Use Case Name} & \textbf{Manage Tasks} \\ \hline
\textbf{XRef} & Section 2.2 — Product Functions \\ \hline
\textbf{Actor} & User \\ \hline
\textbf{Trigger} & The user opens the Tasks (Kanban) tab to organize their work. \\ \hline
\textbf{Precondition} & The user must be authenticated and logged in. \\ \hline
\textbf{Basic Path} & 1. The user navigates to the Tasks board. \newline 2. The system loads existing tasks from the database. \newline 3. The user clicks "Add Task" or drags an existing task to a new column. \newline 4. The system updates the task status locally in Zustand. \newline 5. The system sends an API request to persist the new task state to the database. \\ \hline
\textbf{Alternative Paths} & If the API update fails, the system reverts the local UI state to its previous condition and shows a warning. \\ \hline
\textbf{Postcondition} & The task is successfully created, updated, or moved, and the changes are saved to the backend. \\ \hline
\textbf{Exception Paths} & The user loses internet connection; drag-and-drop actions are disabled or cached locally until reconnected. \\ \hline
\textbf{Other} & The drag-and-drop interaction should be smooth and not block the UI during API calls. \\ \hline
\end{xltabular}

\subsection*{3.3 View Dashboard Progress}

\renewcommand{\arraystretch}{1.5}
\begin{xltabular}{\textwidth}{|p{4cm}|X|}
\hline
\textbf{Use Case Name} & \textbf{View Dashboard Progress} \\ \hline
\textbf{XRef} & Section 2.2 — Product Functions \\ \hline
\textbf{Actor} & User \\ \hline
\textbf{Trigger} & The user navigates to the Dashboard tab. \\ \hline
\textbf{Precondition} & The user must be authenticated. \\ \hline
\textbf{Basic Path} & 1. The user selects the Dashboard view. \newline 2. The system fetches the user's study metrics, task completion data, and active streaks from the API. \newline 3. The system renders charts and summary statistics. \\ \hline
\textbf{Alternative Paths} & If the user has no previous data, the system displays empty states encouraging the user to start a timer or create a task. \\ \hline
\textbf{Postcondition} & The user sees an accurate reflection of their study progress. \\ \hline
\textbf{Exception Paths} & API timeout occurs while fetching statistics; the system displays an error message and a retry button. \\ \hline
\textbf{Other} & Dashboard rendering must be fast and data should be cached locally to minimize loading times. \\ \hline
\end{xltabular}

\subsection*{3.4 Manage Study Timer}

\renewcommand{\arraystretch}{1.5}
\begin{xltabular}{\textwidth}{|p{4cm}|X|}
\hline
\textbf{Use Case Name} & \textbf{Manage Study Timer} \\ \hline
\textbf{XRef} & Section 2.2 — Product Functions \\ \hline
\textbf{Actor} & User \\ \hline
\textbf{Trigger} & The user opens the Timer tab to start a Pomodoro session. \\ \hline
\textbf{Precondition} & The user must be authenticated. \\ \hline
\textbf{Basic Path} & 1. The user navigates to the Timer page. \newline 2. The user selects a session duration. \newline 3. The user clicks "Start Timer". \newline 4. The system begins the countdown. \newline 5. When the timer reaches zero, the system plays an alert sound. \newline 6. The system logs the completed session to the database. \\ \hline
\textbf{Alternative Paths} & The user clicks "Pause" during the session; the timer stops counting down until resumed. The user clicks "Reset"; the timer resets without logging the session. \\ \hline
\textbf{Postcondition} & A study session is completed and recorded in the database. \\ \hline
\textbf{Exception Paths} & The user closes the tab mid-session; the system optionally warns the user or attempts to save partial progress locally. \\ \hline
\textbf{Other} & The timer must rely on robust timestamp calculations to remain accurate if the browser throttles background tabs. \\ \hline
\end{xltabular}

\subsection*{3.5 Use case stories}
\noindent\textbf{UC-01: User Authentication} \\
\textit{As a user, I want to register and log in to the application so that my personal study data and tasks are securely saved and accessible only to me.} \\
\textbf{Acceptance Criteria:} The user can successfully create an account. Passwords are encrypted. Invalid login attempts return an appropriate error message.

\vspace{0.3cm}
\noindent\textbf{UC-02: Manage Tasks} \\
\textit{As a user, I want to create tasks and drag them across different progress columns so that I can visually track what I need to do and what I have finished.} \\
\textbf{Acceptance Criteria:} Tasks can be created and deleted. Tasks dragged to a new column instantly update their status on the frontend and persist to the backend.

\vspace{0.3cm}
\noindent\textbf{UC-03: View Dashboard Progress} \\
\textit{As a user, I want to view a summary of my study statistics on a dashboard so that I can evaluate my productivity over time.} \\
\textbf{Acceptance Criteria:} The dashboard accurately reflects the data from the database, updating whenever a new task is completed or a timer session finishes.

\vspace{0.3cm}
\noindent\textbf{UC-04: Manage Study Timer} \\
\textit{As a user, I want to use a Pomodoro timer to manage my study sessions and breaks so that I can maintain focus and prevent burnout.} \\
\textbf{Acceptance Criteria:} The timer counts down accurately. It provides a visual/audio cue upon completion and logs the session.

\section*{4. Non-Functional Requirements}

\subsection*{4.1 Performance}
\begin{itemize}
    \item The Kanban Board and Timer screens should respond to valid input changes (e.g., drag-and-drop actions) within 1 second on a standard laptop/desktop.
    \item The application should render the Dashboard charts and load user statistics within 2 seconds after successful login, assuming a standard network connection.
    \item Under default settings, the FastAPI backend should support at least 100 concurrent task synchronization requests smoothly.
    \item The system should complete API validation and storage of standard CRUD operations (creating tasks, logging sessions) within a reasonable time (under 500ms) for interactive use.
    \item The application should remain highly responsive while API requests (like task updates) are being processed in the background.
    \item The system must provide a robust timeout mechanism for API calls (configurable; default 10s) to avoid blocking the user interface if the server is unreachable.
    \item Client-side state updates (via Zustand) must be idempotent and avoid redundant network requests when local data is already perfectly synced with the server.
\end{itemize}

\vspace{0.5cm}
\subsection*{4.2 Security}
\begin{itemize}
    \item User passwords must be securely hashed using bcrypt (version 3.2.2 or higher) before being stored in the database.
    \item The system must use JSON Web Tokens (JWT) for authenticating API requests. Tokens must expire after a configurable timeframe (default 24 hours) and be stored securely on the client side.
    \item The backend API must implement robust input validation (via Pydantic) to protect against common SQL and NoSQL injection attacks.
    \item The application must protect against Cross-Site Scripting (XSS) by properly escaping user-generated content before rendering it on the frontend.
\end{itemize}

\vspace{0.5cm}
\subsection*{4.3 Reliability \& Availability}
\begin{itemize}
    \item The system should aim to maintain a high availability rate of 99.9\% during normal operating hours.
    \item In the event of a network failure, the frontend application must gracefully handle offline states, preventing data loss by caching actions (like drag-and-drop or timer completions) locally until the connection is restored.
    \item The backend API must include comprehensive error handling and logging to prevent server crashes and facilitate rapid debugging.
    \item Automated daily backups of the SQLite database should be supported to prevent catastrophic data loss.
\end{itemize}

\vspace{0.5cm}
\subsection*{4.4 Maintainability}
\begin{itemize}
    \item The frontend codebase must be strictly typed using TypeScript, and the backend using Python type hints, to ensure code readability and reduce runtime errors.
    \item The React application must follow a modular, component-based architecture, ensuring that UI elements (Kanban, Timer, Dashboard) are decoupled and easily testable.
    \item The backend API endpoints must be fully documented using auto-generated Swagger/OpenAPI documentation natively provided by FastAPI.
    \item Code must adhere to standard linting and formatting rules (e.g., ESLint/Prettier for React, PEP8/Black for Python).
\end{itemize}

\vspace{0.5cm}
\subsection*{4.5 Portability \& Compatibility}
\begin{itemize}
    \item The web application must be fully responsive and function correctly across major modern web browsers (Google Chrome, Mozilla Firefox, Safari, and Microsoft Edge).
    \item The frontend UI (built with Tailwind CSS) must support seamless switching between Light and Dark modes based on user preference or system settings.
    \item The application must be easily deployable on standard cloud infrastructure (AWS, Heroku, Vercel, etc.) using Docker containers if necessary, without requiring vendor-specific modifications.
    \item The backend API must be OS-agnostic, capable of running smoothly on Windows, Linux, or macOS environments.
\end{itemize}

\section*{5. External Interface Requirements}

\subsection*{5.1 User Interfaces}
\begin{itemize}
    \item The user interface must be a web-based application built with React, ensuring a responsive design that adapts to desktop, tablet, and mobile screens.
    \item The application must feature intuitive drag-and-drop mechanics for task management on the Kanban board.
    \item The Timer page must offer a clean, distraction-free visual aesthetic to maximize user focus during Pomodoro sessions.
    \item The Dashboard must present data using clear visual hierarchies and easy-to-read charts for productivity tracking.
    \item The UI must support standard accessibility guidelines and provide seamless switching between Light and Dark themes via Tailwind CSS.
\end{itemize}

\subsection*{5.2 Software Interfaces}
\begin{itemize}
    \item \textbf{Backend Framework:} The system interfaces with FastAPI (Python) to expose RESTful API endpoints, fully documented via an auto-generated OpenAPI/Swagger UI.
    \item \textbf{Database System:} The application interfaces with a SQLite database for local data storage, abstracted through the SQLAlchemy ORM to allow seamless future migration to PostgreSQL or MySQL.
    \item \textbf{Data Contract:} All data exchanged between the React frontend and the FastAPI backend must be formatted as JSON, with strict validation enforced by Pydantic models.
\end{itemize}

\subsection*{5.3 Hardware Interfaces}
\begin{itemize}
    \item The application does not require any specialized hardware interfaces. It is designed to run on standard consumer devices, including personal computers, laptops, tablets, and smartphones.
    \item Interaction with the system requires standard hardware input devices such as a keyboard, mouse, trackpad, or touchscreen display.
\end{itemize}

\subsection*{5.4 Communication Interfaces}
\begin{itemize}
    \item \textbf{Network Protocols:} All client-server communications must utilize standard HTTP/1.1 or HTTP/2 protocols.
    \item \textbf{Security:} In production environments, all communication must be encrypted using HTTPS/TLS to protect sensitive user data (e.g., passwords, JWT tokens) during transit.
    \item \textbf{Data Format:} The system relies exclusively on REST APIs transmitting JSON payloads for data exchange.
    \item \textbf{Connectivity:} An active Internet connection is required for data synchronization, though the frontend local state (Zustand) can temporarily cache actions during brief network interruptions.
\end{itemize}
